Every captured cache row belonged to device 12 / assignment 32. The API and rendered dashboard HTML matched the real four traffic rates on every valid sample; the baseline displayed dashes. No browser session was available, so visual browser rendering was not independently observed.

Evidence: runtime/controlled-live-samples.jsonl, runtime/controlled-worker.log, runtime/controlled-supervisor.jsonl. The supervisor records normal worker exit, released locks, unchanged device/assignment records and other caches, and disabled gates.

Traffic above 10 PPS cannot be attributed exclusively to one invocation of the 100-packet Kali command. Values are the actual observed counter deltas. No traffic was generated by NetShield.

The worker uses read-only RAW get/print calls. No rules or counters were modified. Windows used one venv launcher and one child interpreter for a single worker; the singleton lock was confirmed held during the run.

An optional --duration-seconds argument was added to the scoped worker, with a regression test for automatic exit. Both polling gates were temporarily enabled by the supervisor and restored to False afterward. No permanent monitoring activation was performed.

Final verification: 12 successful API connections, zero API error entries, one worker start and one automatic duration stop. Worker exit code was 0. The supervisor elapsed time was 121.58 seconds including interpreter startup and observing shutdown; the worker's own deadline was 120 seconds. Process inspection after shutdown found no worker or launcher remaining. Both release flags were verified False in a fresh Django process, and cached presentation returned Not monitored with null rates. Settings still contained a 10-second interval.

Regression validation: 327 Django tests and 8 JavaScript UI tests passed; Django checks reported no issues. Device/assignment records and all other devices' sample caches were unchanged.
